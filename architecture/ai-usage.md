# AI Usage Log

The assessment expects AI assistance. This log records where AI was used and where human judgement shaped or
overrode the output, so every artifact can be explained and defended.

Tool: Claude (Claude Code).

| Step | AI contribution | Human judgement / decision |
|---|---|---|
| Brief analysis | Extracted and summarised the assessment brief; proposed a modular monolith with five modules and a single reference slice | Confirmed approach |
| Mediator choice | Proposed avoiding MediatR (commercial licence) | Proposed Marten; AI clarified Marten is a store, not a mediator, and suggested Wolverine alongside it |
| Persistence | Suggested EF Core initially | Rejected EF Core; chose Dapper + DbUp. AI flagged the overlap with Marten schema management → single Migrator, schema ownership rule |
| Local environment | Proposed Aspire | Required docker-compose as well from day one. AI flagged drift risk and proposed distinct roles |
| Database change policy | — | Introduced the hard rule: additive-only changes, removals in a later release (expand/contract). AI analysed rollback edge cases (dual-write needs 3 releases, triggers 2; events and messages also covered) |
| Rollback strategy | Pointed out that expand/contract alone makes rollback possible but not cheap; proposed feature flags with OpenFeature, multi-state migration flags and flag-driven migration phases | Agreed flags were missing, but judged the full design too complex for an application with no code. Chose simple flags on Microsoft.FeatureManagement for v1, with OpenFeature documented as the target and explicit triggers to move (ADR-0019) |
| Contract timing | Proposed separating code removal from schema drop, and a stabilisation period | Accepted both; default stabilisation of one production release cycle, adjustable per change |
| Order lifecycle | Drafted a retail-style saga (sync availability check, card authorize/capture); then critiqued it (race on "accepted", duplicated saga state, cancellation races, unknown outcomes) | Identified the root cause: no defined domain. Fixed the domain as **B2B** and specified the lifecycle (reserve → invoice due in 3 days → processing → shipping, customer contact states, API vs support cancellation). AI mapped it to states, proposed aggregate-as-process-manager and durable timers, and listed gaps; user accepted the defaults. Assumptions placed centrally in the README at the user's request |
| Closing ADR gaps | Reviewed the Proposed ADRs and found 22 gaps with default recommendations, including: retries at two layers multiplying, fake adapters reaching production, personal data in permanent events, no owner for prices or customer data, unspecified rounding, and no ADRs for API versioning, deployment or testing | Accepted the defaults; chose to add a Customers module and all three new ADRs (0020–0022). One adjustment made while writing: validating unknown SKUs against the price list instead of the external inventory system, to keep external calls out of the request path |
| Phase 0 spikes | Built and ran the seven experiments against real packages and PostgreSQL. Discovered that the current packages (Wolverine 6, Marten 9) are newer than the AI's training knowledge, so APIs were verified via package XML docs, reflection and compiler feedback instead of memory. Debugged its own spike mistakes (handler class naming, status query) before drawing conclusions, and isolated the circuit-breaker stall with a controlled comparison | Required the experiments to be run for real and the plan fixed from their results before any later phase. Design changes from the evidence: register-before-emit and rollback floor (S3), Migrator applying three schema owners with explicit registration (S4), no listener circuit breaker (S7) |
| Delivery workflow | Proposed splitting Phase 1 into three PRs and pointed out that the first two would have no CI | Chose three PRs with manual review, owner-only merges, and required the workflow to be written into the plan (with a PR template) before implementation starts; manual verification evidence per criterion until PR 1c adds automated tests for them |
| Re-plan after Phase 1 | Split Phases 2–4 into 30 small PRs with acceptance criteria, sizes and dependencies; when asked which steps the brief makes mandatory, re-read the brief and mapped each functional requirement to the smallest set of PRs that demonstrates it, noting that design plus Phases 0–1 had already used most of the timebox | Found Phase 1 PRs too large to verify and asked for the re-plan before any more code. Chose the minimum set plus the second half of the state machine (2e) and a real-shaped billing adapter (3c); the rest is kept as ordered next steps for the delivery team |
| PR 1a runtime foundation | Implemented the solution, composition root, Migrator, AppHost, compose, Dockerfiles and Keycloak realm; verified each acceptance criterion by running it (empty database, Migrator twice, compose, AppHost, dashboard traces, real Keycloak tokens). Found and fixed issues only visible at runtime: Npgsql strips the password from `NpgsqlDataSource.ConnectionString` (Migrator could not run DbUp), Wolverine looked for pre-generated code in the wrong assembly (static mode silently fell back to scanning), Kerberos probe noise in Linux containers | Delivery via a reviewed PR; structural deviations (BuildingBlocks split, Composition project, migrator run record) called out in the PR and reflected in README, plan and ADRs |
| PR 1b API conventions, security, flags | Implemented problem details, JSON conventions, OpenAPI, the idempotency filter with Marten records and a Wolverine recurring cleanup, JWT/scope/account policies, per-account rate limiting, the flag adapter and registry, the fake-integration guard and the diagnostics endpoint. Checked Wolverine 6 (recurring cron messages), Marten 9 / JasperFx (concurrency exception types) and Microsoft.OpenApi 2 APIs against the package XML docs. Verified every criterion against real Keycloak tokens locally, in compose (static codegen) and via the AppHost, including the flag event in the dashboard trace, cleanup deleting records and 429s. Found during verification: the realm gave users every scope, so no `403` was possible; the OpenAPI timestamp schema lost its type; an AppHost volume from PR 1a no longer matched the generated Postgres password | Reviewed and merged (#3). Design choices made during implementation are recorded as ADR updates instead of being decided silently: raw-byte request hashing, claim-with-lease and the Phase 2 atomicity gap (ADR-0020), remote-address partition for anonymous callers (ADR-0016), optional user scopes in the realm |
| PR 1c tests and CI | Built the test projects, architecture and migration rules, integration and AppHost tests, and the GitHub Actions pipelines with release compatibility and compose smoke scripts. Probed ArchUnitNET, Wolverine, Marten and Aspire testing APIs by reflection and small experiments, not from memory. Found that generic call arguments are visible to ArchUnitNET (used for document registration), and that the handler graph compiles without a database. Proved every rule by making it fail (illegal module reference, command without handler, unregistered document, `DROP COLUMN` and volatile default scripts, FeatureManagement in a module) and then reverting. Issues found by running things: a vacuous "should not be empty" assertion (tightened to the exact violation); an in-process tracing test exporting other tests' spans (moved to a process); `codegen test` failing inside Wolverine 6.38; Windows 260-character paths for the baseline worktree; a CI-only race between readiness and startup logs | Reviewed and merged (#4). Decisions surfaced instead of taken silently: branch protection is unavailable on the current GitHub plan (making the repository public or upgrading is the owner's call; the definition is prepared); marker interfaces and a pinned names file as the enforcement mechanism for handler coverage and aliases; integration events allowed several handlers (ADR-0015 revised) |
| Phase 2 domain PRs (2a pricing pipeline, 2d / 2d-2 / 2e the Order aggregate) | Implemented the rule pipeline and the full state machine from ADR-0017 and ADR-0018, with table-driven tests over every reachable state × trigger and every disallowed command (227 cases in `Ordering.Domain.Tests`). Raised what the ADR does not settle instead of inventing it: leaving `RequiresAttention` (no target for "reinstatement"), the scope of `CompensationFailed`, and a partial payment after cancellation | Required the ADR gaps to be recorded rather than closed by code; accepted `AttentionResolved → Cancelled` as the v1 exit and kept reinstatement as a business decision (ADR-0017 §2a). 2d was split into 2d-2 during review because it was too large; 2e declared a size overrun and proposed a split, which was accepted as one PR |
| Phase 2 data and slice PRs (2b customers, 2c price lists, 2f submit, 2g read, 2i reserve, 2j cancel) | Built the schemas and seed data, `IPricingService`, the endpoints, handlers, projection and the outbox wiring, each with integration tests against the Migrator-built schema. Several designs were forced by a failing test rather than chosen: the account id on `OrderSubmitted` became a `Guid`, `PriceLine` had to publish the unit price (the rounded line total cannot be divided back), and the reservation handle became the provider's key | Reviewed and merged each PR; deviations that touched an earlier PR's contract were required to be called out in the PR body rather than made quietly. The inactive-account rule is proven on the command rather than over HTTP, because the alternative was adding a Keycloak client and a seeded account from an Ordering PR |
| Framework constraints found while building (PRs 2f, 2i, 2g) | Two architectural constraints surfaced only at runtime, not in the architecture tests: Marten 9 needs its source generator in the assembly declaring the aggregate, which the framework-free domain forbids (streams are folded by hand); and Wolverine's generated handler code cannot construct `internal` adapters or factory-registered services. Added `ProjectionCoverageTests` so a new lifecycle event cannot silently freeze the read model | Accepted both workarounds and required them to be written into ADR-0006 and ADR-0004 as implementation notes, since every future aggregate and handler meets them |
| Phase 3 integration PRs (3a billing port, 3b shipping port, 3c billing HTTP adapter) | Built the ports, the fakes and the WireMock-backed HTTP adapter with its resilience pipeline and anti-corruption mapping. Found that a resilience pipeline resolves `TimeProvider` from the container, so the `FakeTimeProvider` of ADR-0022 stops timeouts and breaker windows from ever elapsing — a test hung until the pipeline was pinned to `TimeProvider.System`. Defined the retryable/rejected split and the unknown-outcome protocol, which ADR-0014 left open | Accepted the split and the added `billing-provider-rejected` code; required the `TimeProvider` trap in ADR-0014 because it applies to every future typed client |
| Diagnosing a test that would not stay green (PR 2j) | A release assertion passed alone and failed about half the time in the full suite. The first two explanations were wrong; the cause was found by dumping the Wolverine tables: no dead letters and the message handled — the hosts share durable queues while each has its own in-memory fake, so the assertion was on the wrong observation point | Required the diagnosis to be evidence-based rather than a guessed fix, and the finding to be recorded in ADR-0022 so the next test on a fake adapter does not repeat it |
| Working in parallel | Several PRs were implemented by background agents in separate git worktrees (2c, 2e, 3c) while another was written in the main clone, each with the plan row and the ADRs as the brief. Agents reported size overruns, scope questions and ADR gaps instead of deciding them | Set the split so that concurrent PRs touched different files, and reviewed every agent result against the merged branch rather than accepting the report; each agent PR was verified independently before merge |
| HTTP layer | Offered Wolverine.Http vs minimal APIs | Chose minimal APIs dispatching messages for separation of concerns |
| Messaging transport | Proposed in-process first | Made in-process conditional on crash durability; otherwise RabbitMQ |
| Documentation | Drafted README, implementation plan and ADRs; PR 4a made the final pass — phase statuses, the implementation notes above, the missing exit from `RequiresAttention` in the README state diagram, and this log | Reviewed; the one open issue is flagged in ADR-0017 §2a and in the plan's open questions rather than left in a PR body |
